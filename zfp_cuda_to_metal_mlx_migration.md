## 1. Goals and non-goals

### Goals

- Add a Metal GPU backend for fixed-rate compression/decompression paths currently served by CUDA.
- Keep public C API source compatibility (`zfp.h` usage patterns unchanged for existing clients).
- Preserve existing dispatch behavior in `zfp_compress` / `zfp_decompress` tables (`src/zfp.c`).
- Maintain correctness first (byte-identity where expected), then optimize.

### Non-goals (initial release)

- No attempt to support every historical Mac GPU generation in v1.
- No immediate expansion to 4D GPU kernels (current CUDA path already omits 4D GPU entries).
- No redesign of core bitstream format or compression semantics.

## 2. Current integration reality (important)

The repo does not call a generic `gpu_compress()` today. Instead:

- `src/zfp.c` uses function tables keyed by execution policy + strided + dims + type.
- CUDA entries are generated by template includes and eventually call:
  - `cuda_compress(stream, field)`
  - `cuda_decompress(stream, field)`
- Those come from `src/cuda_zfp/cuZFP.cu` via `src/template/cudacompress.c` and `src/template/cudadecompress.c`.

Implication for migration:

- We should **not** start by replacing all dispatch machinery.
- The fastest low-risk path is introducing a backend-internal abstraction while preserving the current `compress_*_cuda_*` and `decompress_*_cuda_*` call sites.

## 3. Target architecture

Keep `zfp` external behavior unchanged, but refactor backend internals:

```text
zfp public API (zfp.h) - unchanged
        |
        v
src/zfp.c function tables (unchanged shape)
        |
        v
compress_*_cuda_* / decompress_*_cuda_* wrappers
        |
        v
gpu backend bridge (new internal abstraction)
   |- cuda backend (existing path, refactored)
   |- metal backend (new)

optional:
MLX adapter reusing Metal kernels
```

Key principle: **internal abstraction, not public API churn**.

## 4. Phase 0 - Design freeze and acceptance criteria

**Duration:** 2-3 days

Lock the following before coding:

- Backend selection strategy:
  - Option A (recommended): keep using `zfp_exec_cuda` as the "GPU" policy and bind it to CUDA or Metal at build-time.
  - Option B: add new `zfp_exec_metal` enum value (higher compatibility risk; avoid in first pass).
- Build flags:
  - `ZFP_WITH_CUDA` (existing)
  - `ZFP_WITH_METAL` (new)
  - mutually exclusive in first implementation.
- Hard requirements:
  - Metal backend requires `ZFP_BIT_STREAM_WORD_SIZE=64`.
  - Unsupported configurations fail at configure time.

Acceptance criteria document should define:

- exact correctness tests,
- supported dimensions/types,
- fallback behavior,
- performance baseline metrics.

## 5. Phase 1 - Backend abstraction without API breakage

**Duration:** ~1 week

### 5.1 Add internal backend header

Create internal-only interface (not installed public header):

- `src/gpu_backend.h`

Example:

```c
// internal only
size_t zfp_gpu_compress(zfp_stream* stream, const zfp_field* field);
void   zfp_gpu_decompress(zfp_stream* stream, zfp_field* field);
```

### 5.2 Preserve current template wrappers

Update `src/template/cudacompress.c` / `src/template/cudadecompress.c` to call `zfp_gpu_compress` / `zfp_gpu_decompress` instead of directly calling `cuda_*` functions.

This keeps `src/zfp.c` tables unchanged and minimizes regression surface.

### 5.3 Extract shared host helpers from `cuZFP.cu`

Move pure logic to shared C++ files:

- contiguity checks (`is_contigous1d/2d/3d`, naming preserved initially),
- pointer offset helper (`offset_void`),
- default stride derivation.

Place in:

- `src/gpu_common.h`
- `src/gpu_common.cpp`

### 5.4 Isolate CUDA-specific runtime code

Refactor CUDA-specific pieces into dedicated CUDA TU(s):

- allocation/copies (`cudaMalloc`, `cudaMemcpy`, `cudaFree`)
- device pointer detection (`cuPointerGetAttributes` via helper)
- kernel launch wrappers.

This produces a cleaner baseline to mirror in Metal.


Ensure `.mm` sources are only compiled when Metal is enabled.

Mirror CUDA host orchestration behavior:

- same contiguity checks for host pointers,
- same failure behavior for unsupported non-contiguous host layouts,
- equivalent stream pointer/bit updates expected by `zfp` core.

### 6.4 No new public field tagging API in v1

Do not add `zfp_field_set_metal_buffer(...)` in first pass.
For v1, support host pointers robustly; add explicit GPU-buffer interop API later if needed.

## 7. Phase 3 - Kernel port CUDA -> MSL

**Duration:** ~2.5 weeks

Port kernels from `src/cuda_zfp` to `src/metal_zfp`.

### 7.1 Scope

- encode: 1D/2D/3D
- decode: 1D/2D/3D
- types: float, double, int32, int64
- fixed-rate mode (matching current CUDA path)

### 7.2 Mechanical mapping

- `__global__` -> `kernel`
- `__shared__` -> `threadgroup`
- `__syncthreads()` -> `threadgroup_barrier(...)`
- CUDA index arithmetic -> Metal grid/threadgroup built-ins.

### 7.3 Parameter packing

Pack scalar launch params into structs (`ZFPParams1/2/3`) in constant buffers.

### 7.4 Word/atomic handling

- Use 64-bit word type (`ulong`) to match zfp word assumption for GPU path.
- Use 64-bit atomics where available.
- If fallback is needed, guard with compile-time checks and verify correctness via dedicated overlap stress tests.

### 7.5 Kernel naming convention

Use deterministic function names encoding dim + scalar type to simplify host dispatch.

## 8. Phase 4 - Validation and performance tuning

**Duration:** ~2 weeks

### 8.1 Correctness matrix (must pass)

For each type `{float, double, int32, int64}` and dims `{1,2,3}`:

- contiguous arrays,
- non-multiple-of-4 sizes,
- representative small/medium/large sizes,
- strided layouts that are still contiguous in memory.

Checks:

- GPU compressed stream equals CPU reference stream where deterministic parity is expected.
- Round-trip decompression matches expected semantics:
  - ints exact,
  - floats within expected tolerance for selected mode.

### 8.2 Integration tests

Add CTest coverage for Metal backend (guarded by option):

- backend smoke tests,
- type/dim matrix,
- stride/contiguity behavior parity with CUDA/CPU path.

### 8.3 Performance tuning

Use Xcode Metal tools:

- Metal Frame Debugger,
- Metal System Trace,
- pipeline reflection (thread execution width, threadgroup memory).

Tune threadgroup sizes per kernel family; keep correctness fixed while tuning.

### 8.4 Native MSL optimization workflow (practical)

When bringing up native Metal kernels, optimize in this order:

1. **Establish a stable baseline**
   - Build with `-DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING_FULL=ON -DZFP_WITH_METAL=ON`.
   - Record baseline times from `testZfpCuda{1,2,3}d{Float,Double,Int32,Int64}` and `testzfp`.
   - Use medians over at least 5 runs per test.

2. **Kernel launch geometry first**
   - Start from `threadExecutionWidth`-aligned threadgroup sizes.
   - Sweep 1D/2D/3D kernels separately (e.g., 64/128/256 threads where valid).
   - Keep occupancy and register pressure balanced; avoid oversized threadgroups that reduce active wavefronts.

3. **Memory traffic and layout**
   - Coalesce global loads/stores for block reads and bitstream writes.
   - Stage block-local data in `threadgroup` memory when reuse is high.
   - Minimize host-device copies in the backend path; keep intermediate buffers device-resident when possible.

4. **Bit packing and atomics**
   - Prefer deterministic contiguous bit writes when possible.
   - For overlapping writes, use 64-bit atomics only where required; avoid atomics in non-overlap fast paths.
   - Validate no data races using stressed non-multiple-of-4 shapes and mixed-rate tests.

5. **Specialize by data type/dim**
   - Compile/type-specialize kernels for `{float,double,int32,int64}` and dimensions `{1,2,3}`.
   - Remove runtime branching from inner loops by selecting specialized pipelines at dispatch time.

6. **Profile, then iterate**
   - Use Metal System Trace to identify kernel vs memcpy bottlenecks.
   - Use pipeline reflection to inspect register/threadgroup usage.
   - Only keep changes that preserve correctness matrix and improve median performance.

### 8.5 Suggested perf gates for native MSL readiness

- All correctness tests in Phase 4 pass for native MSL path.
- No regression > 5% vs prior native-MSL baseline on median compress/decompress time for core 1D/2D/3D float tests.
- Demonstrated speedup over serial policy on representative medium/large 2D and 3D workloads.

### 8.6 Repeatable perf command set

Use the perf helper to collect repeated runs and summary statistics:

```bash
python3 tests/perf/run_perf_suite.py --build-dir build-metal --repeats 5
```

For targeted sweeps and CI artifacts:

## 10. Risks and mitigations

### Risk A - Dispatch/API churn destabilizes core

Mitigation:

- keep `src/zfp.c` table shape unchanged,
- avoid new public API in first milestone,
- route through internal backend bridge.

### Risk B - 64-bit atomic portability

Mitigation:

- first-class support target = Apple Silicon,
- strict compile guards,
- dedicated correctness tests for bit-plane write races,
- document unsupported legacy hardware explicitly if needed.

### Risk C - Non-contiguous host arrays

Mitigation:

- preserve existing behavior from CUDA path,
- centralize checks in shared helper,
- test parity with current behavior.

### Risk D - bitstream word-size mismatch

Mitigation:

- configure-time guard for Metal requiring 64-bit word size,
- runtime assert retained in backend path.

### Risk E - Build portability regressions

Mitigation:

- all Metal/ObjC++ code fully option-gated,
- CI adds explicit with/without-Metal jobs on macOS,
- ensure Linux/Windows untouched when Metal disabled.

## 14. Metal acceleration plan

This section describes a prioritized, incremental plan to close the compress performance gap and further improve decompress throughput. Each item is ordered by expected impact and designed to be independently testable.

### 14.0 Guiding principles

1. **Correctness first**: Every optimization must pass the existing 16-test CTest suite before measuring performance. Never merge a perf change that breaks bitstream parity.
2. **Measure before and after**: Use `tests/perf/run_perf_suite.py --repeats 7` and save JSON snapshots. Use `min` for best-case warm kernel performance (median includes cold PSO compilation calls).
3. **One variable at a time**: Each item below is a standalone change. Ship and measure before combining.
4. **The workload is compute-bound**: At 5-8 GB/s on 4-8 MB data, only ~1.5-2% of M1 Max's ~400 GB/s memory bandwidth is utilized. The serial variable-length embedded coding is the bottleneck — not memory bandwidth or host overhead.

### 14.1 Phase A: Eliminate host-side launch overhead ~~(highest impact)~~ [COMPLETED — net neutral]

**Conclusion**: Phase A optimizations (PSO pre-warming, persistent buffer reuse, single command buffer) were implemented and measured. They produced **no meaningful performance improvement** because host overhead is not the bottleneck — the GPU kernel execution itself is. All Phase A changes were reverted. The kernel is compute-bound on the serial bit-by-bit embedded coding.

#### A1. Reuse src/dst MTLBuffer objects across calls

#### B4. SIMD-group cooperation [TODO — next candidate]

**Files**: `src/metal_zfp/pack_unpack.metal`

- Currently each thread processes one entire block independently (1 block = 4/16/64 values). There is no SIMD-group cooperation.
- ZFP's embedded coding is inherently serial *within a block* because each bitplane depends on the group-test of previous planes.
- However, the *gathering* of source data and the *lifting transform* stages are regular and could benefit from SIMD-group loads.
- Investigate:
  - Using `simd_shuffle` to broadcast/gather the 4 values in a 1D block from a SIMD lane.
  - For 3D: using threadgroup shared memory to stage the 64-float block load (coalesced read from device memory into threadgroup, then per-thread lift from threadgroup).
- This requires careful measurement. The current block sizes (4 for 1D, 16 for 2D, 64 for 3D) may not map well to SIMD widths (32 on Apple GPU).

**Expected impact**: Uncertain. 3D blocks (64 values) are the best candidate. May help 5-15% on both compress and decompress.

### 14.3 Phase C: Double/int32/int64 native kernels (expanding coverage)

**Problem**: Non-float types fall back to serial CPU. For double, this is actually *slower* than direct serial because of the backend bridge overhead (0.044-0.078s vs 0.019-0.027s for serial float of similar size).

#### C1. Double codec kernels

**Files**: `src/metal_zfp/pack_unpack.metal`, `src/metal_zfp/metal_runtime.mm`, `src/metal_zfp/metal_backend.mm`

- Port `zfp_encode_block_*d_float` / `zfp_decode_block_*d_float` to double.
- Key differences:
  - `zfp_exponent_float` -> 11-bit exponent extraction for double.
  - Quantization scale: `ldexp(1.0, 62 - emax)` instead of `ldexp(1.0f, 30 - emax)`.
  - Integer representation becomes 64-bit (`long` in MSL), requiring wider lifting transforms.
  - Bit-writer needs to handle 64-bit unsigned values in the bitplane loop.
- Add PSOs and runtime dispatch analogous to float path.
- Add dispatch cases in `metal_backend.mm` for `zfp_type_double`.

**Expected impact**: Eliminates serial fallback for double. Should achieve similar speedup ratios as float.

#### C2. Int32/int64 codec kernels

**Files**: same as C1

- Integer types skip the float-to-fixed-point conversion and exponent coding.
- The block encoder for integers: no exponent header, direct lifting transform on input values, then embedded coding.
- Simpler than float; can reuse most of the encoder infrastructure.

**Expected impact**: Lower priority since int test arrays are small (fast already). Completes coverage.

### 14.4 Phase D: Advanced / speculative optimizations (lower priority)

#### D1. Indirect command buffers for multi-field batching

- If the application compresses multiple fields in sequence, an `MTLIndirectCommandBuffer` could encode all dispatches up front and execute them with a single GPU submission.
- Requires API changes (batch-compress entry point). Out of scope for current correctness-first approach.

#### D2. Asynchronous (non-blocking) dispatch

- Currently `waitUntilCompleted` blocks the CPU. For streaming use cases, the CPU could prepare the next field while the GPU processes the current one.
- Requires signaling infrastructure (semaphores, completion handlers).
- Significant API/lifetime complexity; defer until host overhead is reduced.

#### D3. Shared memory tile loading for 2D/3D

- Load a tile of source data into threadgroup shared memory using coalesced reads, then let each thread within the group access its block from shared memory.
- Reduces device memory traffic for 2D/3D where blocks overlap in the memory layout due to padding.
